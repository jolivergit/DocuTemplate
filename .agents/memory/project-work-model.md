---
name: Project work model
description: User's product definition for shared project phases, proposal documents, and task notes.
---

Project and proposal phases are the same thing. They are associated with fees, but fees are not their only purpose. Proposals are documents, and the customer does not want multiple entries of the same data.

**Why:** The user corrected a plan that separated execution phases from proposal phases and required copying them.

**How to apply:** Plan shared project information and phases reused by tasks and proposal preparation, not separate lists or manual copy/re-entry workflows.

Users should be able to add ad-hoc phases as well.

**Why:** The user explicitly requested ad-hoc phases.

**How to apply:** Support custom project phases without requiring predefined names, a fee, or an existing proposal; reuse the same phase for tasks and any later proposal inclusion.

Phases may or may not have a timeline, such as “5 weeks” or “8–10 weeks.”

**Why:** The user explicitly described phase timelines as optional and gave both single-duration and range examples.

**How to apply:** Support optional phase durations and ranges without requiring fixed calendar dates.

The user did not need the retired standalone project notes saved.

**Why:** The user explicitly rejected retaining the existing notes as history.

**How to apply:** Do not add a legacy-notes archive or restore retired notes. This does not prohibit new general notes in the running project log.

The desired flow is: start a project; pick the team and collaborating companies; pick phases, fees and an optional general timeline; then maintain Work in motion. The team has Project Admin, Project Manager and Designer roles. Each role can have one or many people.

**Why:** The user showed the customer the task-first implementation and reported that it was still clunky, with too many pop-ups.

**How to apply:** Plan around this setup-to-daily-work sequence, inline interaction and a streamlined project page without tabs. Keep existing project statuses. Do not present a separate “shared project phases” section: phase reuse is inherent, not something users should have to manage.

“Work in motion” is a running project log filled in by users and potentially partially filled from known project information. It includes tasks, reminders, meetings and general notes, not only tasks with attached discussion.

**Why:** The customer liked the name but rejected the task-only interface.

**How to apply:** Preserve the name and broaden the work model. Do not force every entry to have task fields or attach general notes to a task.

Avoid redundant indicators on the project page, such as setup “Ready” or log count/sort badges; keep the actual project status.

**Why:** The user found these indicators confusing rather than useful.

**How to apply:** Keep the project context and Work in motion focused on useful information and actions, not extra readiness or display-mode labels.

Use a single place to view and edit project information, rather than separate view-only and editing modes.

**Why:** The user found the two project-detail/setup buttons awkward and chose one toggle for the existing inline fields, keeping save controls and unsaved-change warnings.

**How to apply:** Keep the project-details interaction unified; do not reintroduce a parallel read-only overview with a second editing entry point.
